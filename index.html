01

EDA คือการสำรวจข้อมูลก่อนลงมือทำอะไร

EDA ย่อมาจาก Exploratory Data Analysis แปลตรงตัวว่า "การวิเคราะห์ข้อมูลเชิงสำรวจ" พูดง่ายๆ คือขั้นตอนที่คุณ "เปิดกล่องข้อมูล" ขึ้นมาดูให้ทั่วก่อน ว่าข้างในมีอะไรบ้าง ก่อนที่จะเริ่มสร้างโมเดลใดๆ ทั้งสิ้น

ทำไมต้องทำ EDA ก่อนเสมอ

ลองนึกภาพว่าคุณได้รับข้อมูลลูกค้าจากบริษัทมา แล้วรีบเอาไปเทรนโมเดลทันทีโดยไม่ดูเลยว่าข้างในมีอะไร — คุณอาจไม่รู้เลยว่ามีคอลัมน์ที่ข้อมูลหายไปครึ่งหนึ่ง มีค่าผิดปกติที่พังจากการกรอกข้อมูลผิด หรือมีลูกค้ากลุ่มหนึ่งที่มีจำนวนน้อยมากจนโมเดลไม่มีทางเรียนรู้จากกลุ่มนั้นได้เลย ถ้าไม่ทำ EDA ก่อน คุณจะสร้างโมเดลที่ดูเหมือนทำงานได้ แต่จริงๆ แล้วมีปัญหาซ่อนอยู่ ซึ่งจะมาปะทุตอนเอาไปใช้งานจริง

พูดสั้นๆ EDA คือการ "ทำความรู้จัก" ข้อมูลก่อนตัดสินใจอะไรทั้งนั้น ทั้งเรื่องจะจัดการข้อมูลที่ขาดหายยังไง จะเลือก algorithm ตัวไหน หรือจะสร้าง feature ใหม่อะไรเพิ่ม

ขั้นตอนของการทำ EDA (เรียงลำดับที่ควรทำจริง)

ขั้นที่ 1 — ดูภาพรวมของข้อมูลก่อน (Data Overview)

สิ่งแรกที่ควรทำทันทีที่เปิดไฟล์ข้อมูล คือถามคำถามพื้นฐานกับตัวข้อมูลเอง:

  • ข้อมูลมีขนาดเท่าไหร่ — มีกี่แถว (แต่ละแถวคือ 1 ตัวอย่างข้อมูล เช่น ลูกค้า 1 คน) และมีกี่คอลัมน์ (แต่ละคอลัมน์คือ 1 คุณสมบัติ เช่น อายุ, รายได้, เพศ) ถ้าใช้ library pandas ในภาษา Python จะเช็คด้วยคำสั่ง df.shape
  • แต่ละคอลัมน์เป็นข้อมูลชนิดไหน — เป็นตัวเลข (numeric เช่น อายุ, ราคา), เป็นข้อความ/หมวดหมู่ (categorical เช่น เพศ, จังหวัด), หรือเป็นวันที่-เวลา (datetime) เพราะแต่ละชนิดต้องจัดการต่างกัน เช็คด้วยคำสั่ง df.dtypes หรือ df.info()
  • ลองดูข้อมูลจริงสักหน่อย — เปิดดูแถวแรกๆ (df.head()) หรือสุ่มดูบางแถว (df.sample()) เพื่อให้เห็นภาพว่าข้อมูลจริงหน้าตาเป็นยังไง บางทีก็เจอปัญหาที่ตาเปล่ามองเห็นได้ทันที เช่น ค่าติดลบในคอลัมน์อายุ
  • มีแถวที่ซ้ำกันไหม (duplicate rows) — ถ้ามีข้อมูลซ้ำกันเป๊ะๆ อาจเกิดจากการเก็บข้อมูลผิดพลาด ถ้าปล่อยไว้จะทำให้โมเดลให้น้ำหนักกับข้อมูลชุดนั้นมากเกินจริง เช็คด้วย df.duplicated().sum()

ขั้นที่ 2 — วิเคราะห์ทีละตัวแปร (Univariate Analysis)

Univariate แปลว่า "ตัวแปรเดียว" ขั้นนี้คือการดูแต่ละคอลัมน์แยกกันทีละตัว ไม่เอาไปเทียบกับคอลัมน์อื่นก่อน เพื่อเข้าใจ "ธรรมชาติ" ของแต่ละตัวแปร

ชนิดข้อมูลสิ่งที่ต้องดูเครื่องมือที่ใช้
ตัวเลข (Numeric)ค่าเฉลี่ย (mean), ค่ากลาง (median), ค่าเบี่ยงเบนมาตรฐาน (standard deviation คือค่าที่บอกว่าข้อมูลกระจายตัวมากน้อยแค่ไหน), ค่าต่ำสุด-สูงสุด, ควอร์ไทล์ (quartiles คือจุดแบ่งข้อมูลออกเป็น 4 ส่วนเท่าๆ กัน), ความเบ้ของข้อมูล (skewness)df.describe(), histogram (กราฟแท่งแสดงการกระจายตัว), box plot (กราฟกล่องแสดงควอร์ไทล์และค่าผิดปกติ)
หมวดหมู่ (Categorical)มีกี่ค่าที่ไม่ซ้ำกัน (unique values), แต่ละหมวดหมู่มีความถี่เท่าไหร่, ข้อมูลแต่ละ class เท่ากันไหมหรือเบ้ไปทางใดทางหนึ่งมาก (class imbalance)value_counts(), bar chart (กราฟแท่ง)
วันที่-เวลา (Datetime)ข้อมูลครอบคลุมช่วงเวลาไหนถึงไหน, ความถี่ของข้อมูลตามช่วงเวลาสม่ำเสมอไหมline plot (กราฟเส้น) ตามแกนเวลา

สิ่งที่ต้องสังเกตเป็นพิเศษในขั้นนี้:

  • ความเบ้ (skewness) — คือการที่ข้อมูลกองอยู่ด้านใดด้านหนึ่งของกราฟมากผิดปกติ แทนที่จะกระจายสมมาตรแบบระฆังคว่ำ เช่น ข้อมูลรายได้มักเบ้ขวา (คนส่วนใหญ่รายได้น้อย มีส่วนน้อยที่รายได้สูงมากๆ ลากหางไปทางขวา) ถ้าข้อมูลเบ้มาก บาง algorithm (โดยเฉพาะที่สมมติว่าข้อมูลเป็นโค้งระฆังปกติ) จะทำงานได้ไม่ดี อาจต้องแปลงข้อมูลด้วยฟังก์ชันลอการิทึม (log-transform) ก่อน
  • ข้อมูลไม่สมดุล (class imbalance) — ถ้าเป็นโจทย์ทำนายหมวดหมู่ (classification) แล้วพบว่าหมวดหมู่หนึ่งมีข้อมูล 95% ส่วนอีกหมวดหมู่มีแค่ 5% (เช่น ตรวจจับธุรกรรมทุจริตในบัตรเครดิต ที่ธุรกรรมปกติมีเยอะกว่าธุรกรรมทุจริตมาก) ต้องวางแผนรับมือตั้งแต่ตอนนี้ เพราะโมเดลอาจ "ขี้เกียจ" ทายแต่กลุ่มใหญ่แล้วได้ accuracy สูงลวงตา
วิธีรับมือ Class Imbalance

ถ้าเจอข้อมูลไม่สมดุล มีสิ่งที่ต้องแก้ 2 ระดับ:

ระดับตัวชี้วัด (Metric) — ห้ามใช้ accuracy วัดผลเด็ดขาด เพราะถ้าข้อมูล 95% เป็นกลุ่มเดียวกัน โมเดลที่ทายกลุ่มใหญ่ทุกครั้งก็ได้ accuracy 95% ทั้งที่ไม่ได้เรียนรู้อะไรเลย ให้ใช้ F1-score (ค่าที่รวม precision กับ recall), PR-AUC (Precision-Recall AUC คือค่าพื้นที่ใต้กราฟระหว่าง precision กับ recall เหมาะกับข้อมูลไม่สมดุลมากกว่า ROC-AUC) หรือ Balanced Accuracy (accuracy ที่ปรับถ่วงน้ำหนักตามสัดส่วนของแต่ละ class) แทน

ระดับข้อมูล/โมเดล — ใช้เทคนิค Resampling เช่น Oversampling ด้วย SMOTE (Synthetic Minority Oversampling Technique คือการสร้างข้อมูลสังเคราะห์เพิ่มให้กลุ่มย่อย) หรือ Undersampling (ลดจำนวนข้อมูลกลุ่มใหญ่ลงให้สมดุลกับกลุ่มย่อย) หรือปรับพารามิเตอร์ของโมเดลโดยตรง เช่นตั้งค่า class_weight='balanced' ใน Random Forest หรือ Logistic Regression เพื่อให้โมเดลให้น้ำหนักกับกลุ่มย่อยมากขึ้นโดยอัตโนมัติ

ขั้นที่ 3 — สำรวจข้อมูลที่ขาดหาย (Missing Values Analysis)

ดูว่าแต่ละคอลัมน์มีข้อมูลหายไปกี่เปอร์เซ็นต์ (df.isnull().mean() * 100) และลองดู "รูปแบบ" การหาย เช่น คอลัมน์ A กับ B มักหายพร้อมกันไหม การสังเกตแบบนี้จะช่วยบอกใบ้ได้ว่าทำไมข้อมูลถึงหาย ซึ่งเป็นจุดเริ่มต้นของการวางแผนว่าจะจัดการยังไง (อธิบายละเอียดในหัวข้อถัดไป) เครื่องมือที่ช่วยดู pattern แบบนี้ได้ดีคือ library ชื่อ missingno

ขั้นที่ 4 — ตรวจหาค่าผิดปกติ (Outlier Detection)

Outlier คือค่าที่ผิดแปลกไปจากข้อมูลส่วนใหญ่อย่างเห็นได้ชัด เช่น อายุ 250 ปี หรือราคาสินค้าติดลบ วิธีตรวจหามีหลายแบบ:

  • Box plot (กราฟกล่อง) — เป็นกราฟที่แสดงการกระจายตัวของข้อมูลเป็นภาพ เห็น outlier ได้ง่ายด้วยตาเปล่าเพราะจะโผล่เป็นจุดออกไปนอกกล่อง
  • วิธี IQR (Interquartile Range แปลว่า "พิสัยระหว่างควอร์ไทล์") — คำนวณจากผลต่างระหว่างควอร์ไทล์ที่ 3 (Q3 คือจุดที่ 75% ของข้อมูลอยู่ต่ำกว่า) กับควอร์ไทล์ที่ 1 (Q1 คือจุดที่ 25% ของข้อมูลอยู่ต่ำกว่า) ค่าที่ต่ำกว่า Q1 ลบ 1.5 เท่าของ IQR หรือสูงกว่า Q3 บวก 1.5 เท่าของ IQR จะถือว่าเป็น outlier
  • Z-score — คือค่าที่บอกว่าข้อมูลจุดหนึ่งห่างจากค่าเฉลี่ยกี่เท่าของค่าเบี่ยงเบนมาตรฐาน ถ้าห่างเกิน 3 เท่า มักถือว่าเป็น outlier
ข้อควรระวัง

อย่ารีบลบ outlier ทันทีที่เจอ ต้องถามก่อนเสมอว่า "ค่าผิดปกตินี้เกิดจากความผิดพลาดในการเก็บข้อมูล หรือเป็นเหตุการณ์จริงที่สำคัญ" เช่น ยอดขายที่พุ่งสูงผิดปกติในวันโปรโมชั่นใหญ่ ไม่ใช่ข้อผิดพลาด แต่เป็นข้อมูลจริงที่มีความหมาย ถ้าลบทิ้งไปเฉยๆ โมเดลจะไม่มีทางเรียนรู้เหตุการณ์แบบนั้นได้เลย

ขั้นที่ 5 — วิเคราะห์ความสัมพันธ์ระหว่างตัวแปร (Bivariate / Multivariate Analysis)

Bivariate แปลว่า "สองตัวแปร" ส่วน Multivariate แปลว่า "หลายตัวแปร" ขั้นนี้คือการดูว่าตัวแปรต่างๆ มีความสัมพันธ์กันยังไงบ้าง ไม่ใช่ดูแยกทีละตัวเหมือนขั้นที่ 2 แล้ว

  • ตัวเลข vs ตัวเลข — ใช้ correlation matrix (ตารางแสดงค่าความสัมพันธ์เชิงเส้นระหว่างคู่ตัวแปร มีค่าตั้งแต่ -1 ถึง 1) แสดงผลเป็น heatmap (กราฟความร้อน ที่ใช้สีบอกความเข้มของความสัมพันธ์) ขั้นนี้ยังใช้เช็คปัญหาที่เรียกว่า multicollinearity ได้ด้วย (คือตัวแปรหลายตัวสัมพันธ์กันเองสูงมาก ซึ่งจะอธิบายเพิ่มในหัวข้อถัดไป)
  • ตัวเลข vs หมวดหมู่ — เช่น ดูว่ารายได้เฉลี่ยของแต่ละจังหวัดต่างกันไหม ใช้ box plot แยกตามหมวดหมู่ หรือ group by แล้วหาค่าสรุป (aggregate)
  • หมวดหมู่ vs หมวดหมู่ — ใช้ตาราง cross-tabulation (ตารางไขว้ที่นับจำนวนของแต่ละคู่ค่าที่เกิดขึ้นร่วมกัน, pd.crosstab()) หรือ stacked bar chart (กราฟแท่งซ้อน)
  • ตัวแปรอื่นๆ vs ตัวแปรเป้าหมาย (target) — นี่คือขั้นที่สำคัญที่สุด เพราะ target คือสิ่งที่โมเดลจะต้องทำนาย การดูว่าตัวแปรไหนมีความสัมพันธ์กับ target ชัดเจน จะช่วยให้เดาได้คร่าวๆ ว่า feature ไหนน่าจะสำคัญกับการทำนาย

ขั้นที่ 6 — สรุปข้อสังเกตเป็นสมมติฐานเบื้องต้น

หลังสำรวจครบทุกขั้นแล้ว ควรสรุปสิ่งที่พบเป็นข้อความสั้นๆ เช่น "ตัวแปร X ดูมีผลต่อ target ชัดเจน", "ตัวแปร A กับ B มีความสัมพันธ์กันเองสูงมาก (อาจต้องเลือกใช้แค่ตัวเดียว)", "ข้อมูลไม่สมดุลมาก ต้องระวังตอนเทรนโมเดล" ข้อสังเกตเหล่านี้จะเป็นตัวนำทางในการตัดสินใจขั้นต่อไปทั้งหมด ทั้งการสร้าง feature ใหม่ (feature engineering) และการเลือก algorithm

  • ดู distribution (การกระจายตัว) ของแต่ละตัวแปรเชิงตัวเลข และความถี่ของแต่ละหมวดหมู่แล้ว
  • รู้แล้วว่าคอลัมน์ไหนมีข้อมูลขาดหายบ้าง และขาดหายกี่เปอร์เซ็นต์
  • ตรวจสอบค่าผิดปกติ (outliers) แล้ว
  • ดู correlation (ความสัมพันธ์) ระหว่าง features ด้วยกันเอง และระหว่าง features กับ target แล้ว
  • เช็คแล้วว่าข้อมูลสมดุลไหม (ถ้าเป็นโจทย์ classification)
  • เช็คแล้วว่ามีแถวข้อมูลที่ซ้ำกันไหม
02

การจัดการข้อมูลที่ขาดหาย (Missing Data)

แทบทุก dataset ในโลกจริงจะมีข้อมูลบางส่วนขาดหายไป (missing values) ไม่ว่าจะเพราะคนกรอกแบบสอบถามไม่ครบ เซนเซอร์เสีย หรือระบบบันทึกข้อมูลผิดพลาด การจัดการเรื่องนี้ให้ถูกวิธีสำคัญมาก เพราะถ้าจัดการผิด อาจทำให้โมเดลเรียนรู้ pattern ที่ผิดเพี้ยนไปจากความจริง

ระยะที่ 1 — เข้าใจ "ประเภท" ของการขาดหายก่อน

ก่อนจะเลือกวิธีเติมข้อมูล (imputation) ต้องเข้าใจก่อนว่า "ทำไม" ข้อมูลถึงหาย เพราะเหตุผลที่ต่างกันจะกำหนดว่าควรจัดการต่างกัน นักสถิติแบ่งการขาดหายออกเป็น 3 ประเภทหลัก:

ประเภท (ชื่อเต็ม)ความหมายตัวอย่าง
MCAR
Missing Completely At Random
(ขาดหายแบบสุ่มโดยสมบูรณ์)		การขาดหายเกิดขึ้นแบบสุ่มล้วนๆ ไม่เกี่ยวข้องกับตัวแปรใดเลย ไม่ว่าจะเป็นตัวแปรที่สังเกตได้หรือตัวค่าที่หายไปเองเซนเซอร์วัดอุณหภูมิเสียแบบสุ่มบางวัน ไม่เกี่ยวกับว่าอุณหภูมิวันนั้นสูงหรือต่ำ
MAR
Missing At Random
(ขาดหายแบบสุ่ม โดยสัมพันธ์กับตัวแปรอื่น)		การขาดหายไม่ได้สุ่มล้วนๆ แต่สัมพันธ์กับตัวแปร "อื่น" ที่เรามีข้อมูลอยู่แล้ว ไม่ได้สัมพันธ์กับค่าที่หายไปเองคนอายุน้อยมักไม่กรอกข้อมูลรายได้ในแบบสอบถาม การหายของ "รายได้" สัมพันธ์กับ "อายุ" ซึ่งเรารู้อยู่แล้ว
MNAR
Missing Not At Random
(ขาดหายแบบไม่สุ่ม)		การขาดหายสัมพันธ์กับ "ค่าที่หายไปเอง" นี่คือประเภทที่ยากและอันตรายที่สุด เพราะเราไม่มีทางรู้ค่าที่แท้จริง แต่การหายนั้นมีเหตุผลผูกกับตัวมันเองคนที่มีรายได้สูงมากมักไม่ยอมกรอกข้อมูลรายได้ในแบบสอบถาม การหายของ "รายได้" สัมพันธ์กับตัวค่ารายได้เอง
ทำไมต้องรู้ประเภทนี้ก่อน

ถ้าข้อมูลเป็น MCAR การลบแถวที่ขาดหายทิ้งไปจะไม่ทำให้ผลลัพธ์เพี้ยนมากนัก แต่ถ้าเป็น MNAR (เช่นคนรวยไม่กรอกรายได้) การลบทิ้งจะทำให้ข้อมูลที่เหลือมีแต่คนรายได้น้อย-กลาง ทำให้โมเดลเรียนรู้ภาพที่ผิดเพี้ยนไปจากความจริงทั้งหมด

ระยะที่ 2 — สำรวจก่อนตัดสินใจ (อย่าเพิ่งรีบเลือกวิธี)

  • ดูเปอร์เซ็นต์ข้อมูลที่หายไปในแต่ละคอลัมน์ (df.isnull().mean() * 100)
  • วาดกราฟดู pattern การหาย — สังเกตว่าคอลัมน์ไหนมักหายพร้อมกันเป็นกลุ่ม (ใช้ library missingno) ซึ่งจะช่วยบอกใบ้ว่าน่าจะเป็น MAR หรือ MNAR
  • เช็คว่าคอลัมน์ที่มีข้อมูลหายไปนั้น "สำคัญ" กับสิ่งที่เราจะทำนาย (target) มากแค่ไหน ถ้าสำคัญมากต้องระวังเป็นพิเศษ ไม่ควรลบทิ้งง่ายๆ

ระยะที่ 3 — กลยุทธ์การจัดการ (เรียงจากวิธีง่ายไปซับซ้อน)

วิธีอธิบายใช้เมื่อไหร่
ลบทั้งแถว
(listwise deletion)		ลบทิ้งทั้งแถวข้อมูล ถ้าแถวนั้นมีค่าใดค่าหนึ่งขาดหายเฉพาะเมื่อข้อมูลขาดหายน้อยมาก (ต่ำกว่า 5%) และมั่นใจว่าเป็น MCAR เท่านั้น ไม่งั้นจะเสียข้อมูลโดยไม่จำเป็นและอาจเกิดความเอนเอียง (bias)
ลบทั้งคอลัมน์ตัดคอลัมน์นั้นออกไปเลยทั้งคอลัมน์เมื่อคอลัมน์นั้นมีข้อมูลขาดหายเยอะมาก (ประมาณ 60-70% ขึ้นไป) และไม่ใช่ feature ที่สำคัญกับการทำนาย ไม่มีตัวเลขเปอร์เซ็นต์ตายตัวที่ใช้ตัดสินใจได้ทันที ต้องพิจารณาควบคู่กับความสำคัญของ feature นั้นเสมอ
เติมด้วยค่าเฉลี่ย
(Mean imputation)		เอาค่าเฉลี่ยของทั้งคอลัมน์มาเติมแทนค่าที่หายใช้กับข้อมูลตัวเลขที่มีการกระจายตัวค่อนข้างสมมาตร (symmetric) และไม่มี outlier เยอะ เพราะ outlier จะดึงค่าเฉลี่ยให้เพี้ยนไป
เติมด้วยค่ากลาง
(Median imputation)		เอาค่ากลาง (ค่าที่อยู่ตรงกลางเมื่อเรียงข้อมูลจากน้อยไปมาก) มาเติมแทนใช้กับข้อมูลตัวเลขที่มี outlier หรือมีการกระจายตัวเบ้ (skewed) เพราะ median ไม่ถูกดึงด้วย outlier เหมือนค่าเฉลี่ย
เติมด้วยฐานนิยม
(Mode imputation)		เอาค่าที่พบบ่อยที่สุดมาเติมแทนใช้กับข้อมูลประเภทหมวดหมู่ (categorical) เพราะหมวดหมู่ไม่มีค่าเฉลี่ยหรือค่ากลางให้คำนวณ
เติมด้วยค่าคงที่หรือป้ายกำกับ
(Constant/flag value)		เติมด้วยค่าคงที่ที่ไม่ปนกับข้อมูลจริง เช่น -1 หรือคำว่า "Unknown"ใช้เมื่อ "การขาดหายเอง" มีความหมายสำคัญ (มักเป็นกรณี MNAR) เพราะการเติมด้วยค่าเฉลี่ยจะไปกลบสัญญาณที่ว่า "ข้อมูลนี้เคยหายไป" ทิ้ง
เติมด้วยค่าก่อนหน้า/ค่าถัดไป
(Forward fill / Backward fill)		เอาค่าจากแถวก่อนหน้า หรือแถวถัดไป มาเติมแทนใช้กับข้อมูลอนุกรมเวลา (time series) ที่มีลำดับเวลาต่อเนื่องกัน เช่น ราคาหุ้นรายวัน
KNN Imputer
(K-Nearest Neighbors Imputer)		หาข้อมูล "เพื่อนบ้าน" ที่ใกล้เคียงที่สุด (คำนวณจาก features อื่นที่มีอยู่) แล้วเอาค่าของเพื่อนบ้านมาเติมแทนใช้เมื่อ features ต่างๆ มีความสัมพันธ์กัน จะให้ผลแม่นยำกว่าการเติมด้วยค่าเฉลี่ย/ค่ากลางแบบตายตัว
Iterative Imputer
(หรือเรียกว่า MICE — Multiple Imputation by Chained Equations)		ใช้ความสัมพันธ์ระหว่างหลาย features พร้อมกัน สร้างโมเดลย่อยเพื่อทำนายค่าที่หายไปซ้ำไปซ้ำมาหลายรอบจนค่าคงที่ใช้เมื่อต้องการความแม่นยำสูง และมีเวลา/ทรัพยากรคำนวณเพียงพอ (ใช้เวลานานกว่าวิธีอื่น)
Missing Indicatorเพิ่มคอลัมน์ใหม่เป็นค่า True/False บอกว่าค่าตำแหน่งนี้เคยขาดหายมาก่อนหรือไม่ควรใช้ควบคู่กับวิธี impute อื่นเสมอ เพื่อไม่ให้เสียสัญญาณว่า "ค่านี้เคยหายไป" ซึ่งบางครั้งตัวการขาดหายเองก็มีประโยชน์ในการทำนาย
หลักคิดสำคัญที่สุดของหัวข้อนี้

ไม่มีตัวเลขเปอร์เซ็นต์ตายตัวว่า "ขาดหายเกินเท่านี้ต้องลบทิ้ง" การตัดสินใจต้องพิจารณา 3 อย่างประกอบกันเสมอ คือ (1) ขาดหายไปกี่เปอร์เซ็นต์ (2) feature นั้นสำคัญกับการทำนายแค่ไหน (3) ประเภทของการขาดหายคือ MCAR, MAR หรือ MNAR

ระยะที่ 4 — ข้อควรระวังที่มือใหม่มักพลาด

  • ป้องกัน Data Leakage (การรั่วไหลของข้อมูล) — ต้องคำนวณค่าเฉลี่ย/ค่ากลางที่จะใช้เติม (fit imputer) จาก ชุดข้อมูลเทรน (train set) เท่านั้น แล้วค่อยนำไปเติมทั้งชุดเทรนและชุดทดสอบ (test set) ห้ามคำนวณค่าเฉลี่ยจากข้อมูลทั้งหมดรวมชุดทดสอบก่อนแบ่งข้อมูล เพราะจะทำให้โมเดลแอบ "เห็น" ข้อมูลของชุดทดสอบล่วงหน้า ทำให้ผลประเมินดูดีเกินจริง
  • ลองสร้างคอลัมน์ missing indicator ควบคู่กับการ impute เสมอ เพราะบางครั้งตัว "การขาดหาย" เองก็มีพลังในการทำนาย (predictive power) ที่ไม่ควรทิ้งไปเฉยๆ
  • อย่า impute แล้วลืมเช็คผลกระทบต่อการกระจายตัวของข้อมูล — การเติมด้วยค่าเฉลี่ยบ่อยครั้งทำให้ค่าเบี่ยงเบนมาตรฐาน (variance) ของข้อมูลลดลงอย่างไม่เป็นธรรมชาติ เพราะค่าที่เติมเข้าไปทั้งหมดเหมือนกันหมด
แนวปฏิบัติจริงใน Python — ใช้ sklearn Pipeline

ในทางทฤษฎีเรารู้ว่าต้อง fit imputer จาก train set เท่านั้น แต่ในทางปฏิบัติ มือใหม่มักพลาดโดยไม่รู้ตัว เช่น เผลอเรียก StandardScaler() หรือ impute ข้อมูลทั้ง DataFrame ก่อนจะเรียก train_test_split() หรือก่อนทำ Cross-Validation ซึ่งทำให้ข้อมูลชุดทดสอบ "รั่ว" เข้าไปมีอิทธิพลต่อชุดเทรนโดยไม่ได้ตั้งใจ

ทางแก้ที่แนะนำคือใช้ sklearn.pipeline.Pipeline เสมอ โดยรวมขั้นตอน preprocessing (เช่น imputer, scaler) กับโมเดลไว้เป็นก้อนเดียวกัน แล้วส่ง Pipeline ทั้งก้อนเข้า train_test_split() หรือ Cross-Validation แทนที่จะแยกทำ preprocessing ก่อนด้วยมือ วิธีนี้จะทำให้ทุกขั้นตอนของ Pipeline ถูกคำนวณใหม่ภายในแต่ละ fold โดยอัตโนมัติ ป้องกัน data leakage ได้อย่างแท้จริง ไม่ต้องพึ่งความระมัดระวังของมนุษย์เพียงอย่างเดียว

สมมติฐานของแต่ละ Algorithm

Algorithm แต่ละตัวถูกออกแบบมาด้วย "สมมติฐาน" บางอย่างเกี่ยวกับข้อมูล ถ้าข้อมูลของเราไม่ตรงกับสมมติฐานนั้น โมเดลก็อาจทำงานได้ไม่ดี หรือให้ผลลัพธ์ที่เชื่อถือไม่ได้ แม้จะยังรันโค้ดผ่านโดยไม่มี error ก็ตาม เรื่องนี้ไม่ได้มีแค่ "ข้อมูลต้องเป็นการกระจายแบบปกติ (Normal Distribution คือรูปทรงระฆังคว่ำสมมาตร)" อย่างเดียวเท่านั้น แต่ละ algorithm มีข้อกำหนดของตัวเองที่ต่างกันไป

Algorithmสมมติฐาน / ข้อกำหนดสำคัญ
Linear Regression
(การถดถอยเชิงเส้น)		สมมติว่าความสัมพันธ์ระหว่าง feature กับ target เป็นเส้นตรง (linear) โดยตรง, features ไม่ควรมีความสัมพันธ์กันเองสูงมาก (เรียกปัญหานี้ว่า multicollinearity), ค่าความผิดพลาดของการทำนาย (residuals) ควรเป็นอิสระต่อกันและมีการกระจายตัวคงที่ (homoscedasticity)
Logistic Regression
(การถดถอยโลจิสติก)		ข้อควรระวัง: Logistic Regression ไม่ได้ สมมติว่า feature มีความสัมพันธ์เชิงเส้นกับ target โดยตรง (ต่างจาก Linear Regression) แต่สมมติว่า feature มีความสัมพันธ์เชิงเส้นกับค่า log-odds หรือ logit ของความน่าจะเป็น (เขียนเป็นสูตรคือ ln(p/(1-p)) โดย p คือความน่าจะเป็นของ target) ส่วน features ก็ยังไม่ควรมีความสัมพันธ์กันเองสูงมากเช่นเดียวกับ Linear Regression
Naive Bayesสมมติว่าทุก feature เป็นอิสระต่อกันโดยสมบูรณ์ (conditional independence) — ในทางปฏิบัติสมมติฐานนี้มักไม่จริงเป๊ะ แต่โมเดลก็ยังทำงานได้ดีในหลายกรณีแม้สมมติฐานจะไม่สมบูรณ์แบบ
KNN (K-Nearest Neighbors), SVM แบบ RBF kernel (Support Vector Machine), K-Means, PCA (Principal Component Analysis)ไวต่อขนาด (scale) ของตัวเลขในแต่ละ feature มาก เพราะ algorithm เหล่านี้คำนวณจาก "ระยะห่าง" ระหว่างจุดข้อมูล ถ้า feature หนึ่งมีค่าตัวเลขใหญ่กว่าอีก feature มาก (เช่น รายได้เป็นหลักแสน แต่อายุเป็นหลักสิบ) feature ที่ตัวเลขใหญ่จะครอบงำการคำนวณระยะห่างทั้งหมด จำเป็นต้อง normalize หรือ standardize ข้อมูล (ปรับสเกลให้อยู่ในช่วงใกล้เคียงกัน) ก่อนใช้งานเสมอ
LDA (Linear Discriminant Analysis)สมมติว่าข้อมูลในแต่ละหมวดหมู่ (class) มีการกระจายตัวแบบ Gaussian (โค้งระฆังปกติ) และมีเมทริกซ์ความแปรปรวนร่วม (covariance matrix) ที่เท่ากันในทุก class
Decision Tree, Random Forest, Gradient Boosting
(ต้นไม้ตัดสินใจ, ป่าสุ่ม, การเพิ่มความชันแบบไล่ระดับ)		แทบไม่มีสมมติฐานเรื่องรูปแบบการกระจายตัวของข้อมูลเลย ไม่จำเป็นต้อง normalize ข้อมูลก่อนใช้ และไม่ค่อยไวต่อ outlier มากเท่ากลุ่ม linear model จึงเหมาะกับข้อมูลที่ยุ่งเหยิงหรือมีรูปแบบซับซ้อน
K-Means
(อัลกอริทึมจัดกลุ่มข้อมูล)		สมมติว่าแต่ละกลุ่ม (cluster) มีรูปร่างเป็นทรงกลม (spherical) และมีขนาดใกล้เคียงกัน ถ้ากลุ่มข้อมูลจริงมีรูปร่างยาวรี หรือขนาดต่างกันมาก K-Means จะจัดกลุ่มได้ไม่แม่นยำ
SGD-based models
(SGD ย่อมาจาก Stochastic Gradient Descent แปลว่า การไล่ระดับความชันแบบสุ่ม)		ต้อง standardize ข้อมูลก่อนเสมอ ไม่งั้นกระบวนการคำนวณหาค่าที่เหมาะสม (gradient descent) จะลู่เข้าช้ามาก หรือไม่ลู่เข้าเลย
Neural Networks
(โครงข่ายประสาทเทียม)		ต้อง normalize หรือ standardize ข้อมูลก่อนเสมอ และโดยทั่วไปต้องการข้อมูลจำนวนมากพอสมควรถึงจะได้ผลลัพธ์ที่ดีกว่าโมเดลแบบอื่น ถ้าข้อมูลน้อยเกินไปมักเทรนไม่ได้ผลดี

คำศัพท์สำคัญที่ควรรู้จากตารางนี้

อธิบายคำย่อและศัพท์เทคนิค
Normalize / Standardize
การปรับสเกลของตัวเลขในแต่ละ feature ให้อยู่ในช่วงที่ใกล้เคียงกัน (เช่น ปรับให้อยู่ระหว่าง 0-1 หรือปรับให้มีค่าเฉลี่ย 0 และค่าเบี่ยงเบนมาตรฐาน 1) เพื่อไม่ให้ feature ที่มีตัวเลขใหญ่ครอบงำ feature ที่มีตัวเลขเล็ก
Multicollinearity
ภาวะที่ feature หลายตัวมีความสัมพันธ์กันเองสูงมาก เช่น "ส่วนสูงเป็นเซนติเมตร" กับ "ส่วนสูงเป็นนิ้ว" ซึ่งจริงๆ คือข้อมูลเดียวกัน ทำให้โมเดลเชิงเส้นสับสนว่าควรให้น้ำหนักกับตัวไหน
Homoscedasticity
ภาวะที่ความคลาดเคลื่อนของการทำนาย (residuals) มีการกระจายตัวคงที่ตลอดช่วงของข้อมูล ไม่ใช่กระจายตัวมากขึ้นหรือน้อยลงตามค่าของ feature
Gradient Descent
วิธีการทางคณิตศาสตร์ที่ใช้ค่อยๆ ปรับพารามิเตอร์ของโมเดลทีละนิด เพื่อลดค่าความผิดพลาดลงเรื่อยๆ จนกว่าจะเจอค่าที่ดีที่สุด เปรียบเหมือนการเดินลงเขาทีละก้าวเพื่อหาจุดต่ำสุด
Log-odds / Logit
ค่าที่แปลงมาจากความน่าจะเป็น (probability) ให้กลายเป็นตัวเลขที่มีช่วงตั้งแต่ลบอนันต์ถึงบวกอนันต์ คำนวณจากสูตร ln(p/(1-p)) โดย p คือความน่าจะเป็น การแปลงนี้ทำให้ใช้สมการเชิงเส้นในการโมเดลความน่าจะเป็นได้ ซึ่งเป็นหัวใจของ Logistic Regression

สิ่งที่ต้องเช็คก่อนตัดสินใจเลือก algorithm

  • Feature ต่างๆ มีสเกลตัวเลขต่างกันมากไหม → ถ้าใช่ ต้อง scale ข้อมูลก่อนใช้กับ algorithm ที่คำนวณจากระยะห่าง (distance-based models) เช่น KNN, SVM, K-Means
  • มี multicollinearity ระหว่าง features ไหม → ถ้ามี จะกระทบความแม่นยำของ linear models เป็นพิเศษ
  • ข้อมูลมี outlier เยอะไหม → ถ้าเยอะ tree-based models (เช่น Decision Tree, Random Forest) จะทนทานกว่า linear models
  • งานนี้ต้องการให้อธิบายได้ว่าทำไมโมเดลถึงทำนายแบบนั้น (interpretability) ไหม → ถ้าต้องการ linear models และ tree models จะอ่านและอธิบายได้ง่ายกว่า neural network หรือ SVM ซึ่งเป็นเหมือนกล่องดำที่อธิบายเหตุผลได้ยากกว่า
04

Feature Encoding & Scaling

จากหัวข้อ 03 เรารู้แล้วว่า algorithm หลายตัวมีสมมติฐานเรื่องสเกลของข้อมูล และไม่รับข้อมูลที่เป็นข้อความ หัวข้อนี้คือขั้นตอนลงมือทำจริงเพื่อแปลงข้อมูลให้พร้อมป้อนเข้าโมเดล เป็นสะพานเชื่อมระหว่าง "รู้ว่าทำไมต้องทำ" กับ "เลือก algorithm ตัวไหน" ถ้าข้ามขั้นนี้ไป มักจะเจอ error ทันทีตอนเรียก .fit() เช่น could not convert string to float

Feature Encoding — แปลงข้อมูลหมวดหมู่ให้เป็นตัวเลข

โมเดล machine learning ส่วนใหญ่รับข้อมูลเข้าเป็นตัวเลขเท่านั้น ถ้ามีคอลัมน์ที่เป็นข้อความหรือหมวดหมู่ (categorical) เช่น จังหวัด, เพศ, ระดับการศึกษา ต้องแปลงให้เป็นตัวเลขก่อนเสมอ วิธีแปลงที่นิยมมีดังนี้

วิธีอธิบายใช้เมื่อไหร่
One-Hot Encodingสร้างคอลัมน์ใหม่แยกสำหรับแต่ละหมวดหมู่ แต่ละคอลัมน์เป็นค่า 0 หรือ 1 บอกว่าแถวนั้นเป็นหมวดหมู่นั้นหรือไม่ข้อมูลหมวดหมู่ที่ไม่มีลำดับ (nominal) เช่น จังหวัด, สี และจำนวนหมวดหมู่ไม่เยอะเกินไป เพราะถ้าหมวดหมู่เยอะมาก จะสร้างคอลัมน์ใหม่จำนวนมากตามไปด้วย
Label Encodingแปลงแต่ละหมวดหมู่เป็นตัวเลขจำนวนเต็มเรียงกัน (0, 1, 2, ...)เหมาะกับหมวดหมู่ที่มีลำดับ (ordinal) อยู่แล้ว ควรระวังการใช้กับข้อมูลที่ไม่มีลำดับ เพราะโมเดลบางตัว (โดยเฉพาะ linear model) อาจเข้าใจผิดว่าตัวเลขที่มากกว่าหมายถึง "มากกว่า" ทั้งที่จริงเป็นแค่หมวดหมู่คนละกลุ่ม
Ordinal Encodingคล้าย Label Encoding แต่ผู้ใช้เป็นคนกำหนดลำดับของตัวเลขเองตามความหมายจริงของข้อมูลข้อมูลที่มีลำดับความหมายชัดเจนตามธรรมชาติ เช่น ระดับความพึงพอใจ (ต่ำ-กลาง-สูง) หรือระดับการศึกษา
Target / Mean Encodingแทนแต่ละหมวดหมู่ด้วยค่าเฉลี่ยของ target ในกลุ่มนั้นเหมาะกับหมวดหมู่ที่มีจำนวนมาก (high cardinality) เช่น รหัสไปรษณีย์ ที่ One-Hot Encoding จะสร้างคอลัมน์เยอะเกินไป ต้องระวัง data leakage เป็นพิเศษ เพราะคำนวณจาก target ต้อง fit จากชุดเทรนเท่านั้นเหมือนกับ imputer ในหัวข้อ 02

Feature Scaling — ปรับสเกลของข้อมูลตัวเลข

ตามที่อธิบายไว้ในหัวข้อ 03 ว่า algorithm บางกลุ่ม (KNN, SVM, K-Means, PCA, Neural Network) ไวต่อสเกลของตัวเลขมาก จำเป็นต้องปรับสเกลก่อนใช้งานเสมอ วิธีปรับสเกลที่นิยมมีดังนี้

วิธีอธิบายใช้เมื่อไหร่
Standardization
(Z-score scaling)		ปรับข้อมูลให้มีค่าเฉลี่ย (mean) เท่ากับ 0 และค่าเบี่ยงเบนมาตรฐาน (standard deviation) เท่ากับ 1เหมาะกับข้อมูลที่มี outlier ไม่เยอะมาก เป็นตัวเลือกที่ใช้ได้ดีกับ algorithm ส่วนใหญ่ที่ต้องการ scale เช่น SVM, Logistic Regression, Neural Network
Normalization
(Min-Max scaling)		ปรับข้อมูลให้อยู่ในช่วงที่กำหนดไว้แน่นอน โดยทั่วไปคือ 0 ถึง 1เหมาะเมื่อรู้ขอบเขตค่าต่ำสุด-สูงสุดของข้อมูลแน่นอนอยู่แล้ว เช่นค่าสี pixel ของภาพ (0-255) เหมาะกับ Neural Network บางประเภท แต่ไวต่อ outlier มากกว่า Standardization เพราะ outlier หนึ่งตัวจะดึงขอบเขตของช่วงทั้งหมดให้เพี้ยนไป
Robust Scalingใช้ค่ากลาง (median) และ IQR แทนค่าเฉลี่ยและค่าเบี่ยงเบนมาตรฐาน ในการปรับสเกลเหมาะกับข้อมูลที่มี outlier เยอะ เพราะ median และ IQR ไม่ถูกดึงด้วย outlier เหมือน mean และ std ทำให้ทนทานต่อ outlier ได้ดีกว่าสองวิธีแรก

ลำดับที่ถูกต้องในการทำงานร่วมกับหัวข้ออื่น

  • ทำ Missing Data (หัวข้อ 02) ให้เสร็จก่อน — เพราะ encoder และ scaler ส่วนใหญ่รับค่าที่ขาดหายไม่ได้
  • เลือกวิธี Encoding ให้เหมาะกับความหมายของแต่ละคอลัมน์ (nominal vs ordinal) ไม่ใช่ใช้วิธีเดียวกันหมดทุกคอลัมน์
  • เลือกวิธี Scaling ให้ตรงกับ algorithm ที่จะใช้ตามที่สรุปไว้ในหัวข้อ 03 — ถ้าใช้ tree-based models ข้ามขั้นตอนนี้ได้เลย ไม่จำเป็นต้อง scale
  • ทำทุกขั้นตอนนี้ผ่าน sklearn.pipeline.Pipeline เช่นเดียวกับที่แนะนำไว้ในหัวข้อ 02 เพื่อป้องกัน data leakage โดยอัตโนมัติ

เลือก Algorithm ตัวแรกที่จะลอง

scikit-learn (ไลบรารี Machine Learning ยอดนิยมของภาษา Python) มีแผนภาพชื่อ "Choosing the right estimator" หรือ "การเลือก estimator ที่เหมาะสม" (estimator คือคำเรียกรวมที่ scikit-learn ใช้เรียก algorithm/model) เป็นแผนผังการตัดสินใจแบบขั้นบันได ช่วยให้ผู้เริ่มต้นไม่ต้องเดาสุ่มว่าจะเริ่มลองโมเดลไหนก่อนดี

หลักการอ่านแผนภาพนี้คือ ลูกศรสีส้มที่เขียนว่า "Try next" (แปลว่า "ลองตัวถัดไป") หมายความว่า ถ้าโมเดลที่ลองอยู่ให้ผลลัพธ์ไม่ดีพอ ให้ตามลูกศรนั้นไปลองโมเดลตัวถัดไปในแผนภาพ ไล่ไปเรื่อยๆ จนกว่าจะเจอตัวที่ให้ผลลัพธ์เป็นที่พอใจ

คำถามหลักที่แผนภาพใช้ไล่เรียงตามลำดับ

1
มีข้อมูลมากกว่า 50 ตัวอย่าง (samples) ไหมถ้ามีน้อยกว่านี้ scikit-learn แนะนำให้เก็บข้อมูลเพิ่มก่อน เพราะข้อมูลน้อยเกินไปจะทำให้ประเมินผลไม่น่าเชื่อถือ ไม่ว่าจะเลือก algorithm ไหนก็ตาม
2
ข้อมูลมี label (คำตอบที่ถูกต้อง) ให้เรียนรู้ไหมถ้ามี label ให้ไปทางฝั่ง Supervised Learning (การเรียนรู้แบบมีผู้สอน) ซึ่งแบ่งเป็น Classification (ทำนายหมวดหมู่) หรือ Regression (ทำนายตัวเลข) ถ้าไม่มี label ให้ไปทางฝั่ง Unsupervised Learning (การเรียนรู้แบบไม่มีผู้สอน) เช่น Clustering (การจัดกลุ่มข้อมูล)
3
ถ้ามี label แล้ว ต้องการทำนายอะไรถ้าต้องการทำนาย "หมวดหมู่" เช่น สแปมหรือไม่สแปม → เป็นโจทย์ Classification ถ้าต้องการทำนาย "ค่าตัวเลข" เช่น ราคาบ้าน → เป็นโจทย์ Regression
4
ข้อมูลมีจำนวนมากแค่ไหนถ้าข้อมูลน้อยกว่าประมาณ 100,000 แถว มักแนะนำให้เริ่มจากโมเดลอย่าง Linear SVC (Support Vector Classifier แบบเชิงเส้น) แต่ถ้าข้อมูลเยอะมากกว่านั้น มักแนะนำโมเดลกลุ่ม SGD (Stochastic Gradient Descent) เพราะประมวลผลได้เร็วกว่าเมื่อข้อมูลมีขนาดใหญ่
ตัวอย่างการไล่ตามแผนภาพ

สมมติเรามีข้อมูลลูกค้า 5,000 คน มี label ว่าลูกค้าแต่ละคนจะเลิกใช้บริการหรือไม่ (churn หรือไม่ churn) — นี่คือโจทย์ Classification เพราะทำนายหมวดหมู่ และมีข้อมูลน้อยกว่า 100,000 แถว แผนภาพจะแนะนำให้เริ่มลอง Linear SVC ก่อน ถ้าผลไม่ดี ให้ตามลูกศร "Try next" ไปลอง KNeighbors Classifier ถ้ายังไม่ดีอีก ค่อยไปลอง SVC (แบบไม่เชิงเส้น) หรือ Ensemble Classifiers (โมเดลที่รวมหลายโมเดลย่อยเข้าด้วยกัน เช่น Random Forest) ต่อไปเรื่อยๆ

Train/Test Split เทียบกับ Cross-Validation

หลังจากเทรนโมเดลเสร็จแล้ว เราต้องมีวิธี "วัดผล" ว่าโมเดลทำงานดีแค่ไหน โดยห้ามวัดผลจากข้อมูลชุดเดียวกับที่ใช้เทรน (เพราะโมเดลจะจำข้อมูลนั้นได้ ทำให้คะแนนดูดีเกินจริง) จึงต้องมีวิธีแบ่งข้อมูลสำหรับ "ทดสอบ" แยกออกมาต่างหาก ซึ่งมี 2 แนวทางหลักดังนี้

Train/Test Split (การแบ่งชุดเทรน-ชุดทดสอบ)

คือการแบ่งข้อมูลออกเป็น 2 ก้อนแค่ครั้งเดียว เช่นแบ่ง 80% เป็นชุดเทรน (train set) และ 20% เป็นชุดทดสอบ (test set) โดยปกติจะสุ่มแบ่ง (random split) เทรนโมเดลด้วยชุดเทรน แล้ววัดผลด้วยชุดทดสอบเพียงรอบเดียว

Cross-Validation หรือ CV (การตรวจสอบไขว้)

คือการแบ่งข้อมูลออกเป็น K ส่วนย่อยเท่าๆ กัน (เช่น K=5 หรือ K=10) แล้ววนทำการเทรน-ทดสอบทั้งหมด K รอบ แต่ละรอบจะใช้ส่วนที่ต่างกันเป็นชุดทดสอบ ส่วนที่เหลือเป็นชุดเทรน สุดท้ายนำผลคะแนนจากทุกรอบมาหาค่าเฉลี่ย

ความน่าเชื่อถือของคะแนนต่ำกว่า เพราะคะแนนขึ้นอยู่กับว่าสุ่มแบ่งได้ก้อนไหนมาเป็นชุดทดสอบ อาจได้คะแนนที่ดีหรือแย่โดยบังเอิญสูงกว่า เพราะเป็นค่าเฉลี่ยจากหลายรอบ ช่วยลดความผันผวน (variance) ของการวัดผล
เหมาะกับสถานการณ์ไหนข้อมูลมีขนาดใหญ่มาก (ระดับแสนหรือล้านแถวขึ้นไป) เช่นงาน deep learning หรือช่วง prototype (ทดลองแนวคิดเร็วๆ) ก่อนลงรายละเอียดข้อมูลมีขนาดน้อยถึงปานกลาง (งาน tabular data หรือข้อมูลตารางทั่วไปส่วนใหญ่) และตอนที่ต้องเปรียบเทียบหลายโมเดล หรือปรับจูน hyperparameter (ค่าที่ผู้ใช้กำหนดให้โมเดลก่อนเทรน เช่น ความลึกของต้นไม้ตัดสินใจ)

ข้อควรรู้เรื่องคำศัพท์ K-Fold

คนมักเข้าใจว่า Cross-Validation กับ K-Fold คือสิ่งเดียวกัน แต่จริงๆ แล้ว K-Fold คือ Cross-Validation ชนิดหนึ่ง (เป็นชนิดที่พบบ่อยที่สุด) ในขณะที่ Cross-Validation เป็นคำที่กว้างกว่า ยังมีชนิดย่อยอื่นอีก เช่น Stratified K-Fold (K-Fold ที่รักษาสัดส่วนของแต่ละหมวดหมู่ให้เท่ากันในทุกส่วน), Leave-One-Out (ใช้ข้อมูลแค่ 1 แถวเป็นชุดทดสอบในแต่ละรอบ), และ Time Series Split ที่จะอธิบายต่อไป

กฎง่ายๆ ในการเลือกใช้แนวทางไหน

  • ข้อมูลมีน้อยกว่า 10,000 แถว → ควรใช้ Cross-Validation แทบทุกครั้ง (K=5 หรือ K=10)
  • กำลังเปรียบเทียบหลายโมเดล หรือปรับจูน hyperparameter → ต้องใช้ Cross-Validation เพราะการวัดผลจาก Train/Test Split เพียงครั้งเดียวอาจทำให้เลือกโมเดลผิดจากความบังเอิญ
  • ข้อมูลมีขนาดใหญ่มาก และเป็นโมเดล deep learning ที่ใช้เวลาเทรนนานมาก → ใช้การแบ่งแบบ train/validation/test ครั้งเดียว เพราะไม่มีทรัพยากรพอจะทำ Cross-Validation หลายรอบ
  • สำหรับการใช้งานจริงในโปรดักชัน (production) → แนะนำให้มี 3 ชุดข้อมูลแยกกัน คือ train (สำหรับเทรน), validation (สำหรับปรับจูนระหว่างทาง อาจใช้ Cross-Validation ในขั้นนี้), และ test (เก็บไว้ใช้วัดผลครั้งสุดท้ายเท่านั้น ห้ามแตะต้องก่อนหน้านั้นเด็ดขาด เพื่อป้องกัน data leakage)
ย้ำอีกครั้ง — ใช้ Pipeline เวลาทำ Cross-Validation

เช่นเดียวกับที่อธิบายไว้ในหัวข้อ 02 การทำ Cross-Validation ก็ต้องระวัง data leakage เหมือนกัน ถ้า preprocessing (เช่น StandardScaler หรือ imputer) ถูก fit จากข้อมูลทั้งหมดก่อนแบ่งเป็น K folds จะเกิดการรั่วไหลทันที เพราะแต่ละ fold จะแอบเห็นข้อมูลของ fold อื่นผ่านค่าที่คำนวณไว้ล่วงหน้า วิธีที่ถูกต้องคือห่อ preprocessing และโมเดลไว้ใน sklearn.pipeline.Pipeline เดียวกัน แล้วส่งทั้งก้อนเข้า cross_val_score หรือ GridSearchCV เพื่อให้ scikit-learn คำนวณ preprocessing ใหม่ทุกครั้งภายในแต่ละ fold โดยอัตโนมัติ

กรณีพิเศษ — ข้อมูลอนุกรมเวลา (Time Series) ต้องระวังเป็นพิเศษ

ห้ามใช้ K-Fold แบบสุ่มธรรมดากับข้อมูล Time Series

K-Fold แบบธรรมดาจะสุ่มแบ่งข้อมูลโดยไม่สนใจลำดับเวลา ทำให้บางรอบของการทดสอบ เอาข้อมูล "อนาคต" ไปใช้เทรนโมเดล แล้วให้โมเดลทำนาย "อดีต" ซึ่งเป็นสถานการณ์ที่เป็นไปไม่ได้ในโลกความจริง เพราะตอนใช้งานจริง เราจะไม่มีทางรู้ข้อมูลอนาคตล่วงหน้า ปัญหานี้เรียกว่า data leakage จากอนาคต (future data leakage) ผลลัพธ์ของโมเดลจะดูดีเกินจริงมากตอนทดสอบ แต่พอเอาไปใช้งานจริงกลับทำนายได้แย่กว่าที่คาดไว้มาก

ตัวอย่างที่ทำให้เห็นภาพ: สมมติเรามีข้อมูลราคาหุ้นทั้งปี ถ้าใช้ K-Fold สุ่มแบ่งข้อมูล อาจมีบางรอบที่เอาราคาหุ้นเดือนธันวาคมไปเทรนโมเดล แล้วให้โมเดลทำนายราคาหุ้นเดือนมกราคมของปีเดียวกัน ซึ่งในความเป็นจริงเราไม่มีทางรู้ราคาเดือนธันวาคมล่วงหน้าตั้งแต่เดือนมกราคม

ทางแก้ที่ถูกต้องคือใช้ TimeSeriesSplit ใน scikit-learn ซึ่งเป็นเทคนิคที่เรียกว่า "walk-forward validation" (การตรวจสอบแบบเดินหน้าไปทีละก้าว) หลักการคือ:

  1. เทรนโมเดลด้วยข้อมูลช่วงต้น (เช่น เดือน 1-3)
  2. ทดสอบด้วยข้อมูลช่วงถัดไปทันที (เช่น เดือน 4)
  3. ขยายชุดเทรนให้รวมข้อมูลที่เพิ่งทดสอบไปด้วย (เช่น เดือน 1-4)
  4. ทดสอบด้วยช่วงถัดไปอีก (เช่น เดือน 5) วนแบบนี้ไปเรื่อยๆ

ด้วยวิธีนี้ ชุดเทรนจะเรียงตามเวลาอยู่ก่อนชุดทดสอบเสมอ ไม่มีการสุ่มเด็ดขาด ทำให้การประเมินผลสะท้อนสถานการณ์การใช้งานจริงได้ถูกต้อง

ประเมินผลและรู้ว่าเมื่อไหร่ควรลองโมเดลตัวถัดไป

หลังเทรนโมเดลตัวแรกเสร็จแล้ว จะรู้ได้ยังไงว่ามันทำงาน "ได้ผลดี" หรือ "ไม่ได้ผล" จนควรตามลูกศร "Try next" ไปลองตัวถัดไป หัวข้อนี้จะอธิบายสัญญาณและตัวชี้วัดที่ใช้ตัดสิน

สัญญาณที่บอกว่าโมเดลมีปัญหา และควรทำอะไรต่อ

อาการที่พบความหมายและสิ่งที่ควรทำ
คะแนนต่ำทั้งในชุดเทรนและชุดทดสอบเรียกว่า Underfitting (โมเดลเรียนรู้ไม่พอ) หมายความว่าโมเดลไม่มีความสามารถเพียงพอจะจับ pattern ของข้อมูลได้ ทางแก้คือควรลองโมเดลที่มีความซับซ้อนมากขึ้น หรือเพิ่ม feature ที่มีประโยชน์เข้าไป
คะแนนในชุดเทรนสูงมาก แต่คะแนนในชุดทดสอบต่ำกว่ามากเรียกว่า Overfitting (โมเดลจำข้อมูลเทรนมากเกินไป จนไม่สามารถทำนายข้อมูลใหม่ได้ดี) ทางแก้แรกที่ควรลองก่อนคือปรับ regularization (เทคนิคที่ช่วงคุมไม่ให้โมเดลซับซ้อนเกินไป) หรือปรับ hyperparameter ให้เหมาะสม ยังไม่จำเป็นต้องเปลี่ยนไปใช้ algorithm ตัวอื่นทันที
เทรนโมเดลไม่ผ่าน มี error message ขึ้นมักหมายความว่าข้อมูลไม่ตรงกับสมมติฐานของ algorithm นั้น (ตามที่อธิบายในหัวข้อ 03) เช่น มีค่า missing หลงเหลืออยู่ หรือมี feature ที่เป็นข้อความแต่โมเดลต้องการตัวเลขล้วน
ใช้เวลาเทรนนานเกินไปเมื่อเทียบกับขนาดข้อมูลควรพิจารณาย้ายไปใช้ algorithm ที่ scale (ขยายขนาด) ได้ดีกว่าเมื่อข้อมูลมีปริมาณมาก เช่น เปลี่ยนจาก SVC ไปใช้ SGDClassifier ซึ่งออกแบบมาให้ประมวลผลข้อมูลขนาดใหญ่ได้เร็วกว่า

ตัวชี้วัด (Metric) ที่ใช้วัดผลตามประเภทของงาน

การจะบอกว่าคะแนน "ดี" หรือ "ไม่ดี" ต้องเลือกตัวชี้วัดให้ตรงกับประเภทของงานและสถานการณ์ก่อน ไม่มี metric ตัวไหนใช้ได้กับทุกกรณี

งาน Classification (ทำนายหมวดหมู่)

Metricเหมาะกับสถานการณ์ไหน
Accuracyสัดส่วนที่ทายถูกทั้งหมด เหมาะเฉพาะเมื่อข้อมูลแต่ละ class มีจำนวนใกล้เคียงกัน (balanced) ห้ามใช้ถ้าข้อมูลไม่สมดุล เพราะจะให้ค่าดูดีลวงตา (ตามที่อธิบายไว้ในหัวข้อ 01)
Precisionจากที่โมเดลทายว่า "ใช่" ทายถูกกี่เปอร์เซ็นต์ เหมาะกับงานที่ผลบวกลวง (false positive) มีต้นทุนสูง เช่น ระบบกรองสแปม ที่ไม่อยากให้อีเมลสำคัญถูกเข้าใจผิดว่าเป็นสแปม
Recallจากของจริงที่เป็น "ใช่" ทั้งหมด จับได้กี่เปอร์เซ็นต์ เหมาะกับงานที่ผลลบลวง (false negative) มีต้นทุนสูง เช่น การตรวจจับโรคร้ายแรง ที่พลาดไม่จับได้อันตรายกว่าทายผิดเป็นบวก
F1-scoreค่าที่รวม precision กับ recall เข้าด้วยกัน เหมาะเมื่อต้องการสมดุลระหว่างสองค่านี้ และเหมาะเป็นพิเศษกับข้อมูลที่ไม่สมดุล (class imbalance)
ROC-AUCReceiver Operating Characteristic - Area Under Curve คือค่าที่วัดความสามารถของโมเดลในการแยกแยะสองหมวดหมู่ออกจากกัน ยิ่งใกล้ 1 ยิ่งดี เหมาะกับข้อมูลที่ค่อนข้างสมดุล
PR-AUCPrecision-Recall AUC คือพื้นที่ใต้กราฟ precision-recall เหมาะกับข้อมูลไม่สมดุลมาก โดยเฉพาะเมื่อ class ที่สนใจ (positive class) เป็นกลุ่มส่วนน้อย สะท้อนความจริงได้ดีกว่า ROC-AUC ในกรณีนี้
Balanced Accuracyaccuracy ที่ปรับถ่วงน้ำหนักตามสัดส่วนของแต่ละ class เหมาะกับข้อมูลไม่สมดุลเช่นกัน อ่านและอธิบายให้คนอื่นเข้าใจง่ายกว่า F1/PR-AUC

Metricเหมาะกับสถานการณ์ไหน

R²

อย่าเชื่อคะแนนที่ได้จาก Train/Test Split เพียงครั้งเดียว เพราะอาจเป็นความบังเอิญ ให้ใช้ Cross-Validation (เช่นคำสั่ง cross_val_score ในภาษา Python) เพื่อหาค่าเฉลี่ยที่น่าเชื่อถือกว่า จากนั้นเทียบค่าเฉลี่ยนั้นกับ baseline (เส้นฐานอ้างอิง) ง่ายๆ เช่น DummyClassifier (โมเดลจำลองที่ทายแบบไม่ใช้ความฉลาดใดๆ เลย เช่น ทายหมวดหมู่ที่พบบ่อยที่สุดเสมอ) ถ้าโมเดลของเรายังทำคะแนนได้ใกล้เคียงหรือแย่กว่า baseline นี้ นั่นคือสัญญาณที่ชัดเจนมากว่าควรตามลูกศร "Try next" ไปลองโมเดลตัวถัดไป
